# Branch Scheduler

Agor is built to orchestrate autonomous teammates. The scheduler turns every branch into a programmable surface: attach a cadence, hand it a prompt, and Agor will spin up fresh sessions with full context and the authority to act, just like a human collaborator.

## Why a Scheduler?

- **Automation is everything.** Branches are the durable unit of work in Agor; scheduling keeps them progressing without waiting for a human to click “run.”
- **Supervision becomes routine.** Because Agor’s agents are self-aware (they can see boards, sessions, and metadata) and they have the same MCP access you do, schedules can watch active work and step in when something drifts.
- **MCP makes it limitless.** Pair the scheduler with Slack, GitHub, HubSpot, or any other MCP server and you can move information (or trigger actions) anywhere your tooling reaches.

Think of it as an always-on teammate: “Every morning, look at the last 24 hours of activity, write up a report, and post it in #agor,” or “Every Friday, tidy the Superset branches; if the PR merged, stop the Docker environment and archive the branch record.”

## How Scheduled Runs Work

- **Branch-scoped configuration.** Each branch can store a single schedule (toggleable at any time). All metadata lives with the branch so it survives session churn.
- **Cron-driven cadence.** Each schedule tracks its next run and last trigger.
- **Fresh session per run.** When a run fires, Agor creates a new session titled `Scheduled: <branch>`, stamps `scheduled_run_at` with the planned timestamp, and records run details in `session.custom_context.scheduled_run`.
- **Self-aware execution.** The session launches with the branch + board context, inherits the agent/tool settings you chose, and (with MCP enabled) can take all the actions a user could.
- **Smart reliability.** Runs are deduplicated (two-minute grace window), there’s no backfill flood after downtime (only the most recent missed slot fires), and an optional retention policy keeps history trimmed.

> Each scheduled run leaves behind a complete session transcript, perfect for audits, postmortems, or seeding future prompts.

## Configuring a Schedule

1. **Open the branch modal.** From a board card or the branch list, choose “Open” → `Schedule` tab.
2. **Toggle `Enable Schedule`.** Flip the switch to activate or pause the schedule for that branch.
3. **Set the cadence.**
   - Use the visual cron builder or type directly.
   - A human-readable preview confirms the cadence.
   - Schedules run in UTC today; adjust the cron expression if you need a different local time.
4. **Configure the agent.**
   - Pick the agentic tool (Claude Code, Codex, Gemini) that will own the run.
   - In Advanced settings, select the model, permission mode, and MCP servers/context files to attach.
   - Prefer a permissive permission mode (e.g., `auto`) for unattended automation, otherwise the agent may pause mid-run waiting for approval.
5. **Author the prompt template.**
   - Prompts use Handlebars; you can reference branch, board, or schedule data (see below).
6. **Set retention.**
   - Keep the last _N_ scheduled sessions (0 = keep everything). Older runs are removed automatically.
7. **Save.** The daemon validates the cron, computes the next run, and will handle execution from the next tick forward.

You can edit the schedule whenever you like; changes apply to the next run. Disabling the schedule clears the upcoming run timestamp but preserves your configuration for later.

## Template Variables & Context

Prompt templates render with a full, typed context:

```handlebars
Check
{{branch.pull_request_url}}
for new reviews since
{{schedule.scheduled_time}}. If it merged, stop the Docker environment and archive the branch.
```

Available fields:

- `branch.*` – `name`, `ref`, `issue_url`, `pull_request_url`, `notes`, `custom_context`.
- `board.*` – `name`, `description`, `custom_context` (when the branch is on a board).
- `schedule.*` – `cron`, `scheduled_time`, `retention`, and any advanced configuration snapshot.

Use conditionals or loops (standard Handlebars) to branch based on metadata.

## Supervisory Automation Patterns

- **Ops report bot.** Every 24 hours, call the Slack MCP: summarize new sessions, flag failures, and post to `#agor`.
- **GitHub intelligence.** Nightly, list everything merged in `preset-io/*` via the GitHub MCP, write a changelog, and email it out.
- **Revenue radar.** Weekly, query HubSpot MCP for new leads, enrich with LinkedIn, rank them, and drop the plan in `#sales`.
- **Environment janitor.** Hourly, scan the Superset board; if a “Completed” task’s PR merged, stop its Docker environment and delete the branch record.
- **Dependency upkeep.** Monday at 02:00, run npm updates, execute tests, and open a follow-up session for any failures.

Because MCP is just JSON-RPC, you can bring any service into the loop: Agor’s internal MCP for orchestration, Slack for comms, HubSpot for CRM, or custom servers for bespoke workflows.

## Monitoring & History

- Scheduled sessions appear wherever you normally view sessions, marked with the clock icon. Each run includes:
  - `custom_context.scheduled_run.rendered_prompt` for audit trails.
  - `run_index` to show execution count.
  - A config snapshot in case you tweak the schedule later.
- These audit details (`custom_context.scheduled_run`) are only in the **full** session
  record: `sessions.get`, or a `sessions.find` without `lean`. Lean list rows
  (`lean: true`, marked `read_shape: 'session-list-v1'`) leave them out on purpose, so
  read audits from the full record. The run's `schedule_id` and `scheduled_run_at` stay on
  every row.
- Use retention to keep noise down; the daemon automatically deletes older runs beyond your limit.
- Need to rerun immediately? Manually spawn a session, or adjust/save the cron for a new next run.

## Failure notifications

A failed or timed-out **initial execution Task** creates a durable notification intent.
Each failed occurrence has its own Task ID: settling the same Task again does not create
another notification. This includes an initial execution admitted with Run now. A later
ordinary continuation in the same Session is not a new scheduled occurrence. A successful
execution, user Stop, or unverified containment is not reported as a failed execution.

An administrator can bind exactly one existing Slack gateway in the tenant by setting its
non-secret `config.schedule_failure_alert_target` to `channel:<SLACK_CHANNEL_ID>`. This is
an explicit binding, not an inferred default target. The gateway must be enabled, have
outbound enabled, and allow the destination under its existing channel allowlist. Its
creator must retain access to the failed branch and authority to emit through the gateway.
No new credentials or broader permissions are granted by this setting.

Notifications contain only a fixed failure summary, occurrence time, and authenticated
links to the run Session and Schedule’s branch, labelled with the exact Task/Schedule IDs. They do not include prompts, schedule names, provider logs, or error
text. Sending an alert never pauses or disables a schedule, changes its cadence, resumes a
human pause, or replays a failed job. Retaining or deleting run history does not erase the
notification intent.

Administrators can inspect delivery state through the tenant-scoped
`/schedule-failure-notifications` service (`find`, with bounded `$skip`/`$limit`, and `get`
by exact Task ID):

- `pending`: awaiting an authorized target or a dispatch attempt; `last_error_code`
  identifies configuration/access problems without retaining provider error text.
- `sending`: a durable dispatch fence has been acquired.
- `delivered`: a provider message receipt was returned.
- `uncertain`: the provider effect cannot be confirmed (for example, a crash or lost
  receipt after dispatch began). This requires operator attention and is **not** blindly
  resent, because Slack may already have accepted the message. The failed branch is marked
  as needing attention; this does not pause the schedule. Each alert post uses a bounded,
  single-attempt Slack client, with no SDK retransmission or formatting-fallback post.
  This is not an exactly-once delivery guarantee across ambiguous provider/network failures.

The worker retries pending configuration checks independently of schedule execution.
A proven pre-dispatch rejection or explicit authorization/validation nonacceptance returns
an intent to `pending`, with fresh target and permission checks before another attempt.
Unknown platform/network errors do not authorize a retry. A frozen tenant does not block
other tenants: discovery advances in bounded, stable-key pages and wraps after a finite cycle.
It never retries the scheduled job. No messages are sent until an authorized gateway
binding is configured.

### Reconciling an uncertain alert

Each dispatch claim stores a new opaque attempt ID. Releases, uncertain outcomes and
receipt confirmations must match that exact attempt; replaying an older settlement after
a lost database acknowledgement cannot reopen or complete a newer claim. Uncertainty
and branch attention commit together in a short transaction on both SQLite and PostgreSQL.

A returned receipt is retried as a database settlement, never as another Slack post.
If a write gate or database outage blocks settlement, the worker retains up to 256
content-free outcomes in memory. That cache does not survive a daemon restart; the
durable outbox fence still prevents another send.

For an unresolved `sending` or `uncertain` intent, an administrator can inspect the
original bound Slack channel for the fixed summary and exact failed Task ID. If the
message is present, take its Slack timestamp and submit:

```json
{ "action": "confirm_delivery", "platform_message_id": "1234567890.123456" }
```

to `PATCH /schedule-failure-notifications/<EXACT_TASK_ID>`. The service rechecks the
operator's and gateway creator's branch access, current target binding, and allowlist,
then reads only that exact Slack message. It confirms delivery only when the original
bot identity and Task/Schedule/attempt metadata match the currently observed claim.
A claim that changes during verification rejects the stale confirmation. Legacy messages
without attempt metadata are confirmable only for an unchanged legacy attempt. A tenant write gate is checked again
before persisting the verified receipt. Repeating the same confirmation is idempotent.
No lookup or confirmation sends a message or replays the scheduled job.

If the message cannot be found or verified (including missing Slack history access),
the intent remains unresolved and the branch stays marked for attention. Absence is
not proof of non-delivery: there is deliberately no blind-resend API. Keep the attention
flag until an operator has investigated; confirming delivery never automatically clears
an existing human attention flag.

### Upgrading attempt fencing

The attempt-fencing migration requires an offline cutover using the existing migration
workflow: stop all daemons writing this database before applying it, then start only
the updated version. Do not mix or roll back to unfenced notification writers while
notifications are active. Existing intents and human schedule holds are preserved.

## Best Practices

- **Stay idempotent.** Assume runs might retry; avoid prompts that double-post or delete blindly.
- **Log visibly.** Have agents append notes to the branch or board so humans can see what happened.
- **Permit headless automation.** If you expect the agent to operate unattended, set permission mode to `auto` (or a custom mode that doesn’t prompt) before saving the schedule.
- **Attach the right MCP servers.** Make sure Slack, GitHub, HubSpot, etc. are registered and selected so scheduled agents have the tools they need. Schedules run as the user who created them, so only shared servers or servers that user owns can be attached; saving a schedule with another user's private server is rejected.
- **Keep prompts contextual.** Leverage `branch.custom_context` and board data instead of hard-coded values.
- **Pilot before scaling.** Run the first few executions manually to confirm output before letting it run unattended.

## Troubleshooting

- **“Invalid cron expression.”** The UI validates the expression; edit the expression or pick a preset.
- **No session fired.** Confirm the schedule is enabled and `Next run` is in the past. Remember the two-minute grace window.
- **Agent lacks permissions.** Switch permission mode to `auto` or attach the necessary MCP servers in advanced settings.
- **Timezone surprises.** Everything evaluates in UTC today; adjust the cron or translate from your local time.
