# Boards & Zones

**Boards are 2D spatial canvases for organizing branches.** Like Figma for AI coding work. Drag, group, comment, collaborate in real time.

Instead of linear lists or kanban columns, every [branch](/guide/branches) lives at an `(x, y)` coordinate on a board. Sessions appear as a genealogy tree on the branch card. Multiple users see the same canvas with live cursors.

![Agor board with live collaborator cursors, colorful zones, branch cards, markdown notes, and interactive agent dashboards.](/screenshots/board-hero.png)

_An Agor board staged for an active team: live cursors, roomy workflow zones, branch cards, markdown planning notes, and agent-built dashboards sharing the same canvas._

## Why spatial?

**Your brain remembers space.** You remember:

- "The auth branch is in the top-left corner."
- "Testing sessions cluster on the right."
- "That failed experiment is way down there."

This is location-based memory, the same reason you remember where you parked but forget a shopping list. A 2D board gives every branch and session a _place_. Linear lists discard that.

**Like Figma did for design**, Agor brings spatial collaboration to AI coding:

- Everyone sees the same board.
- Real-time cursors show where teammates are working.
- Drag a branch, teammates see it move instantly.

See **[Multiplayer & Social](/guide/multiplayer-social)** for the full collaboration story (cursors, facepile, comments, attention pulse).

## Zones

**A zone is a spatial region on a board that triggers a templated prompt when a branch is dropped into it.**

Drag a branch into "Code Review" → auto-prompts the agent for review.
Drag into "Needs Tests" → auto-prompts for test generation.
Drag into "Ship It" → auto-prompts for changelog + PR description.

Zones turn your board into a workflow engine. Spatial position _means something_. It triggers behavior.

### How zone triggers work

When you drop a branch into a zone:

1. **Session selection**: which session gets the prompt?
   - **Always create new session** (default): clean slate for the zone's task
   - **Let me pick**: choose which session in the tree has the right context
   - **Most recently active**: usually the session you were just working in

2. **Templated prompt executes**: the zone's Handlebars template renders with dynamic data from the branch, board, repo, and environment.

### Handlebars template variables

Zone prompts have access to:

- **Branch**: `{{ branch.name }}`, `{{ branch.issue_url }}`, `{{ branch.pull_request_url }}`, `{{ branch.unique_id }}`
- **Board**: `{{ board.name }}`, `{{ board.description }}`
- **Session**: `{{ session.title }}`, `{{ session.description }}`
- **Environment**: `{{ environment.url }}`, `{{ environment.status }}`
- **Repo**: `{{ repo.name }}`, `{{ repo.default_branch }}`

### Example zone prompt

```
Review the implementation of {{ branch.issue_url }}.

Check if:
1. All acceptance criteria from the issue are met
2. Edge cases are handled
3. Error messages are user-friendly

If approved, comment on {{ branch.pull_request_url }} with summary.
```

Drop a branch → auto-prompts with issue and PR links pre-filled. **No copy-paste, no forgetting which ticket this was for.**

## Kanban-style flows

The classic pattern: chain zones into a pipeline.

```
[ Triage ]  →  [ Analyze ]  →  [ Build ]  →  [ Review ]  →  [ Ship ]
   issue          plan           code        cross-agent      PR + notes
                                              review
```

Each zone has a different prompt template. Drag a branch across the board and it walks through the workflow, picking up context at every step.

You can also build asymmetric pipelines: a "Stuck" zone that escalates to a different model, a "Spawn 5 reviewers" zone that fans out to multiple agents, a "Generate tests" zone wired to a Codex template.

## Arranging board content

Agor can arrange mixed-size branches, cards, zones, notes, apps, and artifacts without treating every object as the same-sized tile.

- **Tidy a selection:** with the Select tool, drag a marquee from empty canvas or an empty part of a zone. Worktrees, cards, zones, notes, apps, and artifacts can be selected; hold Shift, Command, or Control to add to the selection. Choose **Tidy up** in the selection toolbar for two or more items, including items inside the same zone. Agor fits their measured shapes into a compact deterministic cluster; it does not force heterogeneous items into a square grid. Selecting only zones changes that action to **Arrange zones**: Agor sizes every zone on the board from its measured visible contents, packs those frames together with visible free worktrees, cards, notes, apps, and unlocked artifacts, then re-packs each zone's children for its new frame. Selecting a whole zone treats its contents as one hierarchy so a group drag does not move children twice.
- **Tidy a zone:** select a zone and choose **Tidy up contents** in its toolbar. Pinned branches and cards remain pinned and are laid out relative to that zone.
- **Arrange through MCP:** use `agor_boards_auto_arrange` for top-level objects, `agor_boards_auto_arrange_zone` for one zone, or `agor_boards_arrange_zones` for the same content-sized whole-board cluster used by **Arrange zones**. The whole-board operation includes visible free items and also re-packs zone children; no follow-up call is needed.
- **Maintain a zone:** open the zone settings and switch **Auto Zone** on. The board reflows that zone when items appear, disappear, change ordering metadata, or resize as sessions are added.
- **Collapse one card:** use the collapse button in a worktree or card header. Collapsing hides secondary content — metadata, notes, sessions, descriptions — and keeps the header, so the same button expands the card again. Cards with nothing to hide do not show the control.
- **Collapse a zone:** select a zone and choose **Collapse contents** in its toolbar. Once every pinned item is collapsed the button becomes **Expand contents**; a partially collapsed zone still offers **Collapse contents**, so one click makes the whole zone uniform.
- **Compact through MCP:** use `agor_boards_set_compact` to collapse or expand cards/worktrees by placement ID, zone, type, or across a board. This is shared board presentation state, so collaborators and agents see the same density.

Density is a board mutation like any other: it needs Board Editor or Manager access, and viewers see no density controls.

![A card at full density, showing its description and note beside the collapse button in the header.](/screenshots/board-density-card-expanded.png)

![The same card collapsed to its header row, where the expand button remains available.](/screenshots/board-density-card-collapsed.png)

![A zone toolbar showing the density control beside Tidy up contents.](/screenshots/board-density-zone-collapse.png)

**Arrange contents** and ordinary Auto Zone maintenance use the same compact-cluster solver as MCP. Every positionable item inside the zone participates: pinned worktrees and cards, plus unlocked artifacts, notes, apps, and supported canvas objects whose centers are inside the zone. The solver keeps each measured rectangle at its own size, minimizes the enclosing diameter before area and displacement, and preserves gaps and containment instead of forcing unlike shapes onto row shelves. Repeating an arrangement is a no-op, and sub-grid measurement noise is rounded to the board grid so reload and realtime echoes cannot create churn. Dragging a pinned worktree or card is different: it switches the zone to manual because a move is a durable layout decision.

The browser uses the rendered DOM rectangle. MCP first uses the last browser-measured entity size; an unmeasured worktree uses 500×200, while an unmeasured card uses 380px width and a deterministic height estimate from its persisted content. Canvas objects use their persisted rectangle; invalid or missing values fall back to 600×400 for apps/artifacts, 400px width plus a content-derived height for markdown, and 240×120 for legacy text. All values are grid-rounded before packing.

Zone settings provide two opinionated presentations:

- **Grid** is the full-density presentation. With Columns left on Auto, its arrange action uses compact heterogeneous packing. Choosing a column count is an explicit request for a contained row-and-column layout. Grid respects whatever density each item is already at, so cards you collapsed by hand stay collapsed as the zone reflows.
- **Compact list** collapses each item to a one-row summary and arranges a single readable column. This is useful for dense triage, ranking, and status queues.

Switching a zone from **Compact list** back to **Grid** expands its contents again and re-packs them: the preset collapsed them on the way in, so it restores them on the way out, and the rows it left behind are re-spaced for the taller cards. This happens only when you change the preset, not every time an Auto Zone reflows — that would undo collapses you made deliberately.

![A zone in Compact list, each item collapsed to a single row with its expand button.](/screenshots/board-density-compact-list.png)

![The same zone switched back to Grid: every item restored to full height and re-spaced.](/screenshots/board-density-grid-recovered.png)

Both presentations can sort by current spatial order, priority/rank, workflow status, last updated, creation time, or title, in either direction. Switching a previously-unsorted zone to **Auto Zone** defaults to **Last updated · Descending**, so active work appears first. Use **Columns** to request a fixed grid width or leave it on Auto. **Spacing** is an exact pixel input shared by UI and MCP. **Grow to fit** lets an Auto Zone expand vertically to contain every row; when it is off, the zone keeps the size you chose unless the minimum readable stack needs more room for its exposed headers.

For `agor_boards_auto_arrange_zone`, omitting `columns` uses the compact cluster for pinned entities and geometrically contained canvas objects. Supplying `columns` requests a grid; if that target cannot fit, Agor reports and uses the nearest contained, non-overlapping grid instead of overlapping cards. Set `strictColumns: true` when an exact count must be enforced; then an impossible request returns `applied: false` without moving anything. MCP callers can still request `overflowStrategy: "deck"` explicitly for entity-only contents. By default, archived cards and branches are excluded so MCP lays out the same visible items as the board. The tool also accepts `preset`, `sortBy`, `sortDirection`, and `autoResizeHeight`; use `agor_boards_set_zone_layout` to persist those choices, `gap`, and manual or Auto Zone maintenance.

For a whole-board arrangement, `agor_boards_auto_arrange` uses the same compact heterogeneous packing as **Tidy up**; artifacts participate by default, and `includeCanvasObjects: true` also brings text, markdown, and apps into the cluster. Add `includeZones: true` to arrange zones as ordinary fixed-size containers. Pass `columns` only when you explicitly want a row-major grid. Use `agor_boards_arrange_zones` when zone frames should be derived from their measured children: it packs those frames with visible free board items and re-packs each zone's children in the same operation.

## Multiple boards, one workspace

A workspace can have many boards, one per team, one per project, one per long-running initiative. Boards are independent canvases with their own branches, zones, and members.

Common patterns:

- **Per-project boards**: One board per major product, each with its own zones and team.
- **Per-pipeline boards**: A "PR review" board, a "Bug triage" board, a "Roadmap" board.
- **Solo vs team boards**: Personal scratch board for experiments, team board for shipped work.

## Permissions and branch defaults

When branch RBAC is enabled, a board has one primary owner and two intentionally separate permission sections:

1. **Board access** controls who can see and manage this canvas.
2. **Branch defaults** define the complete permission package inherited by branches on this board.

Board access uses Viewer, Editor, and Manager roles. Seeing a branch associated with a board does not make the board visible, and seeing a board does not reveal branch cards the person cannot access.

Branch defaults use the same roles, file-access choices, and session-sharing editor as a branch override. A branch inherits the entire package or overrides the entire package—session sharing never has its own separate inheritance switch.

Entries point to one person or group. Direct person entries override group membership; otherwise group entries combine. **Others** is a clearly labeled fallback for active workspace members who do not match any named entry.

Primary ownership cannot be reassigned. Managers can maintain access and may
enable shared prompting for branch-home Sessions, but do not become owners.
The workspace preference must also be enabled, and execution-home Sessions are
never shareable.
